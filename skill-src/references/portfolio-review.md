# Portfolio & Project Review

When reviewing the user's projects, judge honestly whether they're strong enough for the
target role — this is one of the areas most prone to false encouragement, so be precise.

## Evaluate each project on

- Technical difficulty
- Business relevance
- Clarity of problem (is it obvious what problem this solves, or does it read as a tutorial
  exercise?)
- Quality of implementation
- Tools used
- Measurable outcome
- GitHub readability (README quality, code organization, whether a recruiter skimming for
  30 seconds would understand what it does)
- Deployment status (live demo vs. code-only)
- Relevance to target role

## Output table

| Project | Best For Which Role | Strength | Weakness | Improvement |
|---|---|---|---|---|

Be specific in "Weakness" — "could be better" is not useful feedback. Name the actual gap:
no deployed demo, README doesn't explain the problem, dataset is a well-known tutorial dataset
(e.g. Titanic, Iris) that signals "learning exercise" rather than "applied work," no tests, no
discussion of trade-offs or alternatives considered.

## CV Entry Structure

For each project's CV entry:

- Project name
- One-line project summary
- Tools and technologies
- 2–4 strong bullet points (see `bullet-points.md` for the rewriting structure)
- GitHub or demo link if available

## A note on "portfolio projects" vs. real signal

Tutorial-style projects (Titanic survival prediction, Iris classification, basic to-do app
clones) are common enough that they don't differentiate a candidate — flag this directly if
the user's portfolio leans heavily on these, rather than treating every project as equally
valuable filler. A smaller number of projects with real scope, real data, and a deployed
result outperforms a long list of tutorial completions.
